# 작업 지시: IVE 처리·검증·확인 역할에 사람 또는 에이전트 배정 — 세 역할 모두 에이전트면 완전 자동화

## 1. 목표

지금 IVE 는 **개발(D) 단계만** 에이전트가 자동으로 한다. 검증(W→V→P)과 확인(P→C→E)은 사람이
Claude Code·화면 도구를 켜 놓고 손으로 한다. 그래서 사람이 자리에 없으면 파이프라인이 선다.

이번 작업의 핵심은 **처리·검증·확인 세 역할 모두에 사람 또는 에이전트를 배정할 수 있게 하는 것**이다.
배정된 쪽이 에이전트면 그 단계는 스캐너가 에이전트를 기동해 자동으로 돌고, 사람이면 지금처럼 사람을 기다린다.
**세 역할을 모두 에이전트로 배정하면 D → V → C 가 사람 없이 끝까지 돈다(완전 자동화).** 별도의 자동화 스위치는 두지 않는다.
각 단계의 증적(스크린샷·A/B 결과)은 이슈에 남고, 사람은 그 증적을 보고 **운영(main) 반영만 승인**한다.

```
이슈 등록(IVE)
  → ① 재현   [확인자] : 증상을 스크립트로 재현, 수정 전 스크린샷 첨부           (신설)
  → ② 개발 D [처리자] : dev-{iid} 브랜치 수정 + MR                              (기존)
  → ③ 검증 V [검증자] : 코드 수준 검증(리뷰·검사·빌드·테스트), 통과 시 **묶음 대기** → 묶음 단위로 staging 에 한 번 푸시(3.5.1)
  → ④ 확인 C [확인자] : staging 배포 후 3엔진으로 재현 스크립트 재실행, 수정 후 스크린샷 → E
  → ⑤ 운영   : 사람이 증적 보고 승인                                 (사람, 변경 없음)
```

**이번 범위는 완전 자동화까지다. 미리보기 환경(MR 별 임시 스택)은 이번에 만들지 않고 다음 작업으로 미룬다(8장).**
화면 확인은 staging 이 맡는다. A/B 는 「같은 staging 의 머지 전(①에서 실패) / 머지 후(④에서 통과)」로 성립시킨다.
대가: 화면에서만 드러나는 결함은 staging 에 머지된 뒤 ④에서 잡힌다.

## 3. 구현 요건

### 3.0 역할 배정 — 사람 또는 에이전트 (이번 작업의 중심)

**지금 상태(확인됨)**: 사람에게 역할을 주는 기능이 없다.
- 에이전트 탭의 「검증자」 목록은 프로젝트 Git 멤버(`project_members`) **전원이 자동으로** 들어온다(`getVerifiersList`, `src/lib/db/issues.ts`). 누구를 검증자로 둘지 고르는 기능이 없다.
- 사람 권한은 `project_shares.role = viewer | editor` 뿐이다. 확인자 목록은 없다. 처리자는 에이전트만 가능하다.
- `roles` 테이블은 레거시(참조하지 않음)다 — 재사용하지 말고, 필요하면 새로 설계한다.

**3.0.1 역할 명부(roster) — 먼저 만든다**
- 프로젝트별로 「누가 어떤 역할을 할 수 있는가」를 정하는 명부. 한 줄 = (프로젝트, 대상, 역할들).
  - 대상: **사람**(IVE 사용자 또는 Git 멤버) 또는 **에이전트**(`agents`).
  - 역할: 처리 · 검증 · 확인 — **복수 선택**(한 사람이 검증과 확인을 겸할 수 있다).
- 관리 화면: 프로젝트 설정에 「역할」 탭 — 멤버·에이전트 목록에서 역할 체크. 권한은 프로젝트 소유자·editor.
- 기존 데이터 이행: 지금 검증자 목록에 자동으로 보이던 Git 멤버는 **검증 역할로 이행**해, 적용 직후 화면이 달라지지 않게 한다. 확인 역할은 이슈 작성자 기본값(`creator`)이 이미 쓰이고 있으니 그대로 둔다.
- 에이전트 탭: 필터를 「전체 / 처리 / 검증 / 확인」으로 바꾸고, 각 필터에 **그 역할을 가진 사람과 에이전트를 함께** 보여 준다(역할별 대기·진행 건수 포함 — 지금 검증자 카드의 집계 방식을 확인에도 적용).
- `auto` 모드(부하가 가장 적은 사람 자동 선택)는 **그 역할 명부 안에서만** 고른다(지금은 프로젝트 멤버 전원이 대상).

**3.0.2 사람이 처리자인 경우** — 지금은 없는 흐름이다.
- IVE 는 에이전트를 기동하지 않고 D 단계에서 그 사람에게 배정(Git assignee)한 채 기다린다.
- 완료 판정: 그 사람이 `dev-{iid}` 브랜치로 MR 을 올리면(또는 IVE 화면의 완료 버튼) W 로 넘어간다. 판정은 스캐너가 DB 상태로 한다(스캐너 원칙).

**3.0.3 이슈별 배정**
- **세 역할**: 처리자(D) · 검증자(V) · 확인자(C, ① 재현 포함). 각 역할의 후보는 **3.0.1 명부에서 그 역할을 가진 사람과 에이전트**다.
- 기존 preset 모드(`creator | auto | specific`)에 **에이전트 지정**을 더한다(예: 모드 `agent` + `agentId`, 또는 `specific` 의 대상 종류를 사람/에이전트로 확장 — 기존 데이터와 호환되는 쪽으로 설계하고 근거를 보고).
  처리자도 같은 모델로 올린다(지금은 프로젝트-에이전트 배정만 있다).
- 배정 시점: 이슈 시작(등록·스케줄) 때 세 역할을 정한다. 프로젝트별 **기본 배정**을 두어 이슈마다 고르지 않아도 되게 한다. 진행 중 교체 가능(완료 이슈는 기존처럼 변경 금지).
- **「모든 단계 자동배정」 한 번으로 끝낸다.** 이슈 시작 시 이 선택 하나로 처리자·검증자·확인자를 **한꺼번에 에이전트로** 지정한다(역할마다 따로 고르지 않는다).
  - 각 역할은 명부에서 그 역할을 가진 에이전트 중 **현재 부하가 가장 적은 에이전트**로 고른다.
  - 처리자 ≠ 검증자 제약을 이 자동배정이 지킨다. 명부에 에이전트가 모자라 제약을 못 지키면 배정하지 않고 이유를 보여 준다.
  - 역할 중 하나라도 에이전트 후보가 없으면 그 역할만 비워 두고 알린다(나머지는 배정).
  - 프로젝트 기본값으로 둘 수 있다 — 기본값이 「모든 단계 자동배정」이면 이슈 등록만으로 끝까지 돈다.
  - 자동배정 뒤에도 개별 역할을 사람·다른 에이전트로 바꿀 수 있다.
- **확인자 역할을 화면에 드러낸다.** 지금은 검증자만 보이고 확인자는 사실상 없다 — 에이전트 탭·이슈 등록 폼·이슈 카드에서 세 역할을 같은 모양으로 다룬다.
- 스캐너 동작: 이슈가 어떤 단계에 들어왔을 때 **그 단계의 배정이 에이전트면 단계 작업자를 기동**하고, 사람이면 지금처럼 기다린다(알림은 기존 `slack-notify`).
- **같은 이슈에서 처리자 에이전트와 검증자 에이전트는 같은 에이전트일 수 없다**(자기 작업을 자기가 검수하지 않는다). 배정 시 막는다.
- 사람이 배정된 기존 흐름(화면 단계 버튼, glab 라벨 이동, 외부 Claude Code 세션의 ive-meta 집계)은 그대로 동작해야 한다.
  **아무도 에이전트로 바꾸지 않은 프로젝트의 동작은 지금과 달라지면 안 된다.**

**3.0.4 역할별 프롬프트 관리**
- 지금 에이전트 프롬프트는 `src/lib/scanner/prompt-builder.ts` 에 코드로 박혀 있고 처리(개발)용 하나뿐이다.
  역할이 1급 개념이 되었으므로 **프롬프트를 역할에 붙인다: 처리자용 · 검증자용 · 확인자용**(확인자용은 ① 재현과 ④ 확인 두 벌).
- 층: **IVE 기본값**(코드에 내장, 초기값) → **프로젝트별 덮어쓰기**(IVE 화면에서 편집) → **대상 저장소 지침**(`.ive/verify.md` 등, 실행 시 덧붙임).
- 프롬프트는 두 부분으로 나눈다:
  - **편집 가능한 부분** — 작업 방식·검수 기준·말투 등. 프로젝트 설정 「프롬프트」 탭에서 역할별로 편집.
  - **IVE 고정 부분(편집 불가)** — 결과 판정 형식(통과/반려와 사유), `<!-- ive-meta stage: … -->` 블록, 증적 첨부 규약, 금지 사항(브랜치·main 머지 금지 등).
    스캐너가 이 출력을 파싱해 단계를 옮기므로 사용자가 지우면 흐름이 멈춘다. 화면에는 읽기 전용으로 보여 준다.
- 변경 이력을 남긴다(누가·언제·무엇을). 각 실행 기록(`task_executions`)에 **그때 쓴 프롬프트 판**을 적어, 반려율 변화를 프롬프트 변경과 대조할 수 있게 한다.
- 기존 처리 프롬프트(`buildPrompt`)의 동작은 기본값으로 그대로 옮긴다 — 덮어쓰기가 없는 프로젝트는 지금과 똑같은 프롬프트를 받아야 한다(회귀 금지, 문자열 비교로 확인).

### 3.1 단계 작업자(Stage Worker) 일반화
- D 단계의 실행 파이프라인(워크스페이스 → CLI → 결과 처리)을 **단계 종류(kind)** 로 일반화한다:
  `reproduce` · `dev`(기존) · `verify` · `confirm`.
- 단계마다 **프롬프트 빌더, 허용 도구, 최대 턴, 시간 제한, 결과 판정 방법**이 다르다. kind 별 설정으로 둔다.
- 단계마다 새 세션으로 기동한다(앞 단계의 대화 맥락을 넘기지 않는다 — 넘기는 것은 이슈·MR·증적뿐).
- 실행 행은 기존 `task_executions` 에 `ex-reproduce-` / `ex-verify-` / `ex-confirm-` 접두로 남기고,
  토큰·비용은 기존 보고서 집계에 그대로 잡혀야 한다(`stage-records.ts` 와 일관).
- 스캐너 원칙(CLAUDE.md)을 지킨다: **스캐너는 DB 상태로 판단한다.** 단계 작업자 기동 여부도 DB 상태로 결정한다.

### 3.2 프로젝트 설정 — 안전장치
- 자동화 여부는 3.0 의 역할 배정으로 정해진다. 프로젝트 설정에는 안전장치만 둔다.
- `agentMergeToStaging`(기본 꺼짐): 꺼져 있으면 묶음(3.5.1)이 **출발 직전에서 멈추고** 사람 승인을 기다린다(검증 판정과 증적은 남긴다).
  초기 운용은 꺼 둔 채로 반려율을 본 뒤 켠다.
- **main(운영) 머지는 어떤 설정으로도 자동화하지 않는다.**
- 자동 실행 대상 이슈 작성자 허용 목록: 외부(Service Desk 등)에서 들어온 이슈는 본문이 곧 프롬프트이므로
  허용 목록에 없는 작성자의 이슈는 사람이 한 번 승인하기 전에는 어떤 단계도 자동 실행하지 않는다.

### 3.3 대상 저장소가 제공하는 계약 파일
IVE 는 여러 프로젝트를 다룬다. **"어떻게 띄우고 어떻게 확인하는가"는 대상 저장소가 알려 준다.**
대상 저장소 루트의 `.ive/` 디렉토리를 읽는다(없으면 해당 단계 자동화 불가로 처리하고 사람에게 넘김):

| 파일 | 용도 |
|---|---|
| `.ive/verify.md` | 검증 에이전트용 저장소별 지침 — 돌릴 검사 명령(린트·타입·빌드·단위/골든 테스트), 금지 사항. **IVE 컨테이너 안에서 외부 서비스(DB·Redis 등) 없이 도는 명령만** 적는다 |
| `.ive/staging.json` | staging URL, **배포된 커밋을 알려 주는 주소와 필드**(dazzlepf: `/version.json` 의 `commit`), 테스트 계정 환경변수 이름 |
| `.ive/e2e/` | 재현 스크립트 위치 규약(예: `.ive/e2e/issue-<iid>.spec.ts`) |

- 비밀값(테스트 계정 비밀번호 등)은 파일에 쓰지 않는다. IVE 프로젝트 설정에 암호화 저장(기존 AES-256-GCM 방식)하고
  단계 실행 시 환경변수로만 넣는다.

### 3.4 ① 재현(reproduce)
- 담당: **확인자.** 확인자가 처음(수정 전 실패)과 끝(수정 후 통과)을 함께 쥐어, 처리자가 자기 기준을 만들어 스스로 통과시키지 못하게 한다.
- 트리거: 이슈가 S 단계에 들어오고 확인자가 에이전트일 때, D 보다 먼저. 확인자가 사람이면 재현 스크립트는 선택(사람이 첨부한 스크린샷이 수정 전 증적).
- 할 일: 이슈 본문·첨부 이미지(`issue-images.ts`)로 증상을 이해 → staging 에서 Playwright 로 증상을 재현하는
  스크립트를 `.ive/e2e/issue-<iid>.spec.ts` 로 작성 → **현재 staging 에서 실패하는 것**을 확인 → 수정 전 스크린샷을 이슈에 첨부.
- 재현 스크립트는 `dev-{iid}` 브랜치에 개발 작업보다 먼저 커밋되어 D 단계 에이전트에게 넘어간다(D 는 이 스크립트를 통과시키는 것이 목표).
- 재현 실패(증상을 못 만든 경우): 이슈에 이유를 남기고 **사람 필요 상태**로 보낸다(3.7). 추측으로 D 를 시작하지 않는다.
- 화면이 아닌 이슈(데이터 확인형 등)는 재현 스크립트 대신 `.ive/verify.md` 가 정한 확인 명령(전/후 값 비교)을 쓴다.

### 3.5 ③ 검증(verify)
- 트리거: D 완료로 W 단계에 들어오고 검증자가 에이전트일 때. `start_verification` 전이를 에이전트가 수행한다.
- 할 일, 순서대로:
  1. MR diff 라인 단위 리뷰(요건 대비 누락·축소, 범위 밖 변경, 명백한 결함).
  2. `.ive/verify.md` 가 정한 검사 명령 실행(린트·타입·빌드·테스트). **서버를 띄우지 않는다.**
  3. 재현 스크립트(`.ive/e2e/issue-<iid>.spec.ts`)가 MR 에 들어 있고, 수정 내용이 그 스크립트가 재는 증상을 겨누는지 리뷰한다(실행은 ④에서).
  4. MR 이 staging 최신본 위에 있는지(리베이스 필요 여부) 확인한다 — ④의 A/B 가 성립하는 전제다.
- 판정:
  - 통과 → `approve`. **바로 머지하지 않는다** — 이슈를 「묶음 대기」에 올린다(3.5.1). `agentMergeToStaging` 이 꺼져 있으면 묶음 출발 전에 사람 승인을 받는다.
  - 실패 → `reject`(→ S). 반려 사유와 실패 증적을 이슈 코멘트로 남기고, 다음 D 실행의 피드백(`latestFeedback`)으로 들어가게 한다.
- 결과 코멘트 끝에 `<!-- ive-meta stage: verify ... -->` 를 남겨 기존 `stage-records.ts` 가 집계하게 한다.

### 3.5.1 묶음 배포 — staging 푸시는 묶어서 한 번

**배경(실측, kojoung/dazzlepf)**: staging 푸시 파이프라인이 2026-09-27~30 사이 44회(하루 약 12회).
한 번에 잡 실행 약 10분 + 러너 대기 최대 16분(성공 20건의 전체 소요 중앙값 약 27분).
`build-staging` 은 `resource_group: staging-app` 으로 한 번에 하나만 돌고, 뜬 화면 검사가 돌 때는 최대 ~80분 기다린다.
굽기 끝의 `compose up --force-recreate` 로 staging 이 약 30초 끊긴다 — 도는 중인 확인 작업이 깨진다.
검증 통과마다 푸시하면 자동화로 늘어난 머지가 이 줄에 끝없이 쌓인다.

- **새 상태 「묶음 대기」**(V 통과 ~ staging 푸시 사이). 검증 통과 이슈는 여기에 쌓인다. 화면에 묶음 대기 목록과 다음 출발 예정을 보여 준다.
- **출발 조건**(프로젝트 설정, 먼저 오는 것): 대기 N건(기본 5) · 마지막 추가 후 T분 조용(기본 30) · 정해진 시각(선택).
  **한 번에 한 묶음만 떠 있는다** — 이전 묶음의 파이프라인과 확인(④)이 끝나기 전에는 출발하지 않는다. 묶음 크기 상한(기본 10).
- **출발 절차**: 전용 워크스페이스에서 staging 최신본 위에 대기 MR 들을 차례로 머지 →
  충돌 나는 이슈는 묶음에서 빼고 처리자에게 되돌린다(충돌 분석은 기존 `buildConflictPrompt` 흐름 재사용) →
  합친 결과로 `.ive/verify.md` 검사 1회 → 통과하면 **staging 에 한 번 푸시**. 검사 실패면 묶음을 반으로 나눠 원인 이슈를 찾는다(되돌림은 그 이슈만).
- 푸시 뒤 각 MR 이 GitLab 에서 머지 상태로 잡히는지 확인한다(안 잡히면 API 로 닫고 머지 커밋을 코멘트로 남긴다 — 어느 쪽인지 실측해 보고).
- `merge-watcher` 는 이슈가 아니라 **묶음 단위**로 파이프라인을 감시하고, 성공하면 묶음 안 이슈들의 확인자(④)를 기동한다(동시 상한 3.9).
- 확인 결과: 한 건 실패 → 그 이슈만 되돌린다(되돌리는 커밋은 다음 묶음에 실린다). 여러 건 동시 실패 → 「staging 이 깨졌다」로 사람 필요(3.7), 다음 묶음 보류.
- 사람이 IVE 밖에서 staging 에 직접 푸시하는 것도 막지 않는다 — 묶음 출발 시점의 staging 최신본 위에 쌓을 뿐이다.

### 3.6 ④ 확인(confirm)
- 트리거: P 단계이고 **이 이슈가 실린 묶음의 staging 배포가 완료된 뒤**(`merge-watcher` 성공, 또는 `.ive/staging.json` 의 판정 방법), 확인자가 에이전트일 때.
  (Phase 1 에서는 묶음 배포가 아직 없으므로 사람이 머지한 이슈의 배포 완료로 기동한다.)
  `merge-watcher` 는 지금 Slack 수신자가 없으면 감시하지 않는다(`if (!initiator.slackUserId) return`) — 자동 확인에서는 수신자와 무관하게 감시가 돌아야 한다.
- 할 일:
  1. **배포 확인**: staging 이 실제로 내보내고 있는 버전(SHA)에 이 이슈의 머지 커밋이 들어 있는지 확인한다.
     들어 있지 않으면 기다린다(판정하지 않는다). 확인 방법은 `.ive/staging.json` 이 정한다(버전 엔드포인트 등).
     판정은 `git merge-base --is-ancestor <머지 커밋> <배포된 커밋>` 으로 한다(묶음·후속 머지가 얹혀도 성립).
     dazzlepf 는 이미 있다(실측 2026-09-30): `GET http://www.meta-shops.com:7429/version.json` →
     `{"version":"…","envName":"Staging","commit":"<40자 SHA>","builtAt":"…"}` — `commit` 이 `origin/staging` 최신과 일치했다.
  2. **화면 확인(탐색)**: 확인자 에이전트가 **Playwright MCP**(`@playwright/mcp`, `--headless`, `--browser chrome|firefox|webkit`, 모바일은 `--device`)로
     staging 을 직접 열어 이슈가 말한 경로를 사람처럼 클릭해 가며 본다. 접근성 트리만으로 판정하지 않는다 —
     겹침·잘림·넘침 같은 시각 결함은 트리에 안 보이므로 **스크린샷을 찍어 눈으로 보고**, 의심되면 요소 크기·위치를 재서 수치로 확인한다.
     증상과 무관한 새 결함을 보면 반려 사유에 함께 적는다.
  3. **화면 확인(반복 판정)**: 재현 스크립트를 Chromium·WebKit·Firefox 3엔진으로 실행 → 전부 통과 → 수정 후 스크린샷·trace 첨부.
     판정의 근거는 이 스크립트 결과다(2는 스크립트가 놓치는 것을 잡는 보조).
  4. **A/B 판정**: ①에서 같은 스크립트가 머지 전 staging 에서 실패한 기록이 있어야 한다. 실패 기록 없이 통과만 있으면 인과 미증명으로 사람 필요(3.7).
- 같은 묶음·그사이 다른 머지가 함께 staging 에 올라가 있다. 여러 이슈의 확인이 **동시에** 실패하면
  이슈별 재작업으로 돌리지 말고 「staging 이 깨졌다」로 판정해 사람 필요(3.7)로 보내고 알린다(3.5.1 과 같은 규칙).
- 이슈에 **증적 코멘트 하나**를 남긴다: 수정 전/후 스크린샷 표, 엔진별 통과 여부, 실행한 명령, 커밋 SHA, MR 링크.
- 통과 → `accept`(→ E). 실패 → `return_to_dev`(→ W 또는 S), 실패 증적 첨부. 되돌리는 수정은 다음 묶음에 실린다.
- 결과 코멘트 끝에 `<!-- ive-meta stage: confirm ... -->`.

### 3.7 사람에게 넘기는 출구
- 새 단계 상태 **「사람 필요」** 를 둔다(라벨 이름은 프로젝트 설정, 기본 `IVE-H`). 다음 경우 이 상태로 보낸다:
  재현 실패, A/B 불성립, staging 동시 실패, 같은 이슈가 **2회 연속 반려**, `.ive/` 계약 파일 없음, 시간·턴·비용 상한 초과, 허용 목록 밖 작성자.
- 진입 시 Slack 으로 이유와 함께 알린다(`slack-notify.ts`). 사람이 조치 후 기존 단계로 되돌리는 전이도 `stage-transitions.ts` 에 추가한다.
- 무한 순환 금지: 이슈별 자동 순환 횟수 상한을 설정으로 둔다.

### 3.8 증적 저장
- 스크린샷·Playwright trace 는 GitLab/GitHub 업로드 API 로 올려 이슈 코멘트에 마크다운으로 붙인다.
  업로드 헬퍼는 `provider.ts` 계층에 GitLab/GitHub 공용으로 둔다.
- 원본 파일은 `data/evidence/<projectId>/<iid>/<stage>-<timestamp>/` 에도 보관하고, IVE 이슈 상세 화면에서 단계별로 볼 수 있게 한다.

### 3.9 동시성·자원
- 단계 작업자 동시 실행 수 상한(전역·프로젝트별, kind 별). Playwright 3엔진을 띄우는 ①·④ 는 기본 2.
- 이슈별 워크스페이스는 단계마다 분리한다(`workspaces/<projectId>/issue-<iid>-<stage>`). 서버 재시작 시 고아 브라우저 프로세스를 정리한다(`resetStuckExecutions` 와 같은 자리).
- 외부로 여는 포트는 없다. 모든 브라우저 접속은 IVE 에서 staging 공개 주소로 나가는 연결뿐이다.

### 3.10 화면
- 프로젝트 설정: 「역할」 탭(3.0.1 명부) · 「프롬프트」 탭(3.0.4) · 기본 배정(「모든 단계 자동배정」 포함) · 묶음 배포 설정(3.5.1) · 안전장치(3.2)·상한값.
- 에이전트 탭: 전체/처리/검증/확인 필터(3.0.1).
- 이슈 등록 폼·이슈 카드: 처리자·검증자·확인자 세 칸, 「모든 단계 자동배정」 선택.
- 묶음 대기 목록과 다음 출발 예정, 진행 중 묶음(3.5.1).
- 이슈 상세: 단계별 실행 로그(기존 xterm 재사용)와 증적 갤러리(전/후 나란히).
- DESIGN_GUIDE.md 를 따른다. i18n(ko/en) 모두 추가.

## 4. 단계적 진행 — 한 번에 다 하지 않는다

각 Phase 가 끝날 때마다 멈추고 결과를 보고한다. 다음 Phase 는 승인 후 진행한다.

1. **Phase 1 — 3.0 역할 명부·사람 처리자·이슈별 배정(확인자 노출 포함) + 단계 작업자 일반화 + ④ 확인.** 확인은 코드를 건드리지 않아 위험이 가장 낮다. 사람이 P 까지 옮긴 이슈에 확인자 에이전트를 배정해 자동 확인·증적 첨부.
2. **Phase 2 — ① 재현(확인자).**
3. **Phase 3 — ③ 검증자 에이전트(코드 수준) + 3.5.1 묶음 배포.** `agentMergeToStaging` 은 꺼진 채(머지 직전 정지)로 먼저 운용.
4. **Phase 4 — 3.7 출구·순환 상한·화면 마무리.**

Phase 1~4 가 끝나면 이슈 등록 → 재현 → 개발 → 검증 → 묶음 배포(staging) → 확인 → 완료가 사람 없이 돈다(완전 자동화). 여기까지가 이번 작업이다.

첫 적용 대상 프로젝트는 `kojoung/dazzlepf`(Meta-Shop)이다. 이 저장소용 `.ive/` 계약 파일 초안도 Phase 1 산출물에 포함하되,
**그 저장소에는 커밋하지 않고** 파일 내용만 보고에 첨부한다(그 저장소 소유자가 반영한다).

## 5. 제약

- **git 브랜치를 새로 만들거나 전환하지 않는다.** 현재 체크아웃된 브랜치에서 작업하고, 커밋·푸시는 요청받았을 때만 한다.
- 기존 수동 흐름(화면 단계 버튼, glab 로 라벨 옮기기, 외부 Claude Code 세션의 ive-meta 집계)이 **그대로 동작해야 한다.**
- 기존 D 단계 동작은 바뀌면 안 된다(회귀 금지). 일반화 리팩터링 후 기존 D 실행을 실제로 한 번 돌려 확인한다.
- 임시방편 덧대기 금지(CLAUDE.md). 스캐너 분기를 kind 마다 복붙하지 말고 공용 경로로.
- 비밀값을 로그·코멘트·증적 파일명에 남기지 않는다. CLI 로그에서 토큰 마스킹을 확인한다.
- CHANGELOG `## [Unreleased]` 에 기록한다. 새 통합 기능이므로 릴리스 시 minor.

## 6. 완료 기준 (Phase 별로 전부 「예」여야 보고)

1. 이 문서의 해당 Phase 요건이 1:1 로 구현되었나 — 요건 목록과 대조표를 보고에 붙인다.
2. 구현한 것이 전부 실제로 실행되었나 — **테스트 프로젝트에 실제 이슈를 만들어** 해당 단계를 끝까지 돌린다.
   단위 테스트(vitest)는 보조이고 검증이 아니다.
3. 결과가 화면에서 보이나 — IVE 화면(설정·이슈 상세·증적 갤러리)과 GitLab 이슈 코멘트를 브라우저로 열어 확인한다.
4. 자동화를 **꺼 둔** 프로젝트가 이전과 똑같이 도는지 확인했나(회귀).
5. 남은 문제·확인 못 한 구간이 있으면 목록으로 함께 낸다. 확인 못 했으면 「확인 못 했다」고 쓴다.

## 8. 이번 범위 밖 — 다음 작업: 미리보기 환경

이번에는 **구현하지 않는다.** 다만 나중에 붙일 수 있게, ③ 검증 작업자에 「검사 후 추가 단계」를 끼울 자리만 열어 둔다(빈 확장점, 동작 없음).
아래는 다음 작업을 위해 합의된 방향이다 — 이번 작업자는 참고만 한다.

- **목적**: 화면에서만 드러나는 결함을 staging 머지 **전에** 잡는다.
- **이슈마다 상주 환경을 두지 않는다.** 검증하는 몇 분만 빌려 쓰는 **슬롯 풀 + 대기열**. 부하는 슬롯 수로 고정된다.
- **바뀐 앱만 띄운다**(변경 경로로 등급 분류): web 만 → 정적 빌드만 올리고 공용 검증 API 사용 / api 포함 → API 프로세스 1개 + 공용 DB·Redis /
  extractor → 화면 아님, 표본 문서 추출 작업으로 전/후 비교 / DDL·여러 앱 → 전용 슬롯에서 직렬 전체 스택.
- **A 쪽(수정 전)은 따로 띄우지 않는다** — staging 이 수정 전이다(MR 이 staging 최신본 위라는 전제).
- **외부 포트를 열지 않는다.** 미리보기는 IVE 와 같은 호스트의 127.0.0.1 또는 외부 공개 없는 도커 내부 네트워크에만 둔다.
  사람이 봐야 할 때만 기존 443 리버스 프록시의 서브도메인으로, IVE 로그인 뒤에서.
- **운영 서버에서 돌리지 않는다**(staging·운영이 같은 서버). 슬롯 수는 검증 호스트 자원을 실측해 정한다.

# IVE 이슈 처리 (처리자)

> 짝 스킬: 처리 `ive-handle` · 검증 `ive-verify` · 확인 `ive-confirm`. 단계 라벨의 뜻과 규칙의 이유는 CLAUDE.md 의 「IVE 단계 라벨」 절이 원본이다 — 이 스킬과 다르게 적혀 있거나 프로젝트 자체 규칙이 있으면 그쪽을 따르고 라벨 이름·단계 순서만 이 스킬을 따른다.

기본은 사용자가 말한 건만 처리한다. 대기 건을 스스로 찾아 줄줄이 시작하지 않는다 — 단 사용자가 「IVE 처리 루틴 돌려」 라고 했으면 아래 「처리 루틴」을 따른다.

## 체크리스트 — 이 순서대로

1. **대상을 정한다.** 사용자가 번호를 말했으면 그 이슈. 없으면 `glab api "projects/kojoung%2Five/issues?labels=ive%3Atodo&state=opened"` 로 처리대기 목록을 보여 주고 어느 건인지 묻는다.
2. **첫 동작 = 단계 이동.** 코드를 읽기 전에 `ive:todo` → `ive:doing`(개발 중). 이미 `ive:doing` 면 건드리지 않는다. 이동 뒤 라벨을 다시 읽어 **단계 라벨이 하나만** 남았는지 본다.
   ```bash
   glab api --method PUT "projects/kojoung%2Five/issues/<번호>" -f "remove_labels=ive:todo" -f "add_labels=ive:doing"
   ```
3. **요건 목록을 먼저 쓴다.** 이슈 본문과 **모든 코멘트**(보완·지난 반려 지시·「🔁 반려 반복」)를 시각 순으로 읽고 요건을 한 줄씩 적는다. 마지막 정정이 우선이다. 반려된 건이면 지난 지시 항목을 전부 한 번에 끝낸다.
4. **프로젝트 규칙을 먼저 연다.** CLAUDE.md·AGENTS.md 의 다른 절과 건드릴 영역의 규칙 파일을 읽는다.
5. **브랜치.** `dev-<번호>` 에서 작업한다(이미 있으면 이어서 — 반려 건). 이 프로젝트의 목표 브랜치는 `main` 입니다. 새 브랜치를 만들기 전에 사용자에게 한 줄로 알린다.
6. **요건을 전부 구현한다.** 축소·누락 금지. 같은 유형의 결함은 한 곳이 아니라 전수로 고친다.
7. **되는 검수는 다 한다.** 테스트는 **기준선(변경 전) → 변경 후 → A/B(새 테스트는 두고 소스만 되돌려 실패하는지)** 세 단으로, 명령은 절대경로로 돌린다. 이슈에 적힌 대상(문서·레코드·URL)이 있으면 합성 재현으로 끝내지 말고 실제 값으로 전/후를 잰다(읽기만).
8. **못 하는 검수는 「확인 요청」으로 넘긴다.** 앱 서버·DB·화면·운영 접근처럼 이 환경에 없는 것은 노트에 **어디서 · 순서 · 고쳐졌을 때/아닐 때 보이는 것 · 필요한 데이터·계정 · 먼저 할 일(DDL 등)** 을 적는다. 「화면 검수 못 함」 한 줄은 넘김이 아니다.
9. **커밋하고 MR/PR 을 올린다.** 푸시·MR 생성 전에 사용자에게 한 줄로 확인한다. MR/PR 본문에는 이슈 번호만 언급하고 ⛔ `Closes #번호` 같은 닫기 키워드는 쓰지 않는다 — 머지로 이슈가 닫히면 확인 단계가 통째로 건너뛰어진다.
10. **결과 노트를 남기고 `ive:doing` → `ive:verify-wait`(검증 대기).** 노트에 **요건↔수정 대조표**, 기준선/변경 후/A/B 수치, 실측 전/후, 「확인 요청」, 못 한 것(「확인 못 했다」와 「문제없다」는 다르다)을 적는다. 이슈는 **닫지 않는다.**
    ```bash
    glab issue note <번호> -R kojoung/ive --message "$(cat note.md)"
    glab api --method PUT "projects/kojoung%2Five/issues/<번호>" -f "remove_labels=ive:doing" -f "add_labels=ive:verify-wait"
    ```
11. **`ive-meta` 를 남긴다.** 이슈 본문 또는 노트 끝에 처리 시간·토큰을 `ive-meta` 블록으로 남긴다(형식과 idle 제외 방법은 CLAUDE.md 「메타데이터」). 없으면 이 작업의 시간이 0 으로 집계된다.
12. **막히면 우회하지 말고 멈춘다.** 권한 거부·요건 모호·환경 없음이면 라벨은 `ive:doing` 에 두고 필요한 것과 이유를 노트·보고에 적는다.
13. **보고는 10줄 이내.** 첫 줄에 결과(완료·보류) + 현재 라벨 + 브랜치·커밋. 확인한 것만 쓴다.

## 처리 루틴 — 「IVE 처리 루틴 돌려」 라고 했을 때만

**나에게 담당자로 지정된** `ive:todo` 이슈를 5분마다 찾아 위 체크리스트로 처리한다. 담당자가 없거나 다른 사람·에이전트인 건은 건드리지 않는다(IVE 가 에이전트에 배정한 건과 겹치지 않게).

1. 사용자가 간격을 따로 말하지 않으면 `/loop 5m <아래 프롬프트>` 로 등록한다(세션이 열려 있는 동안만, 7일 뒤 만료). 등록 전에 `CronList` 로 같은 루틴이 이미 있는지 보고 있으면 중복 등록하지 않는다. 등록 직후 한 번 바로 돌린다.
2. 매 회차: `glab api "projects/kojoung%2Five/issues?labels=ive%3Atodo&state=opened"` 로 조회해 **내가 담당자인 건**만 고른다. 이미 `dev-<번호>` 브랜치가 있는 건(진행 중)과 제목이 «[진척 관리]» 인 추적 이슈는 제외한다. 반려돼 `ive:todo` 로 돌아온 건은 제외하지 않고 기존 브랜치에서 이어서 한다.
3. **건마다 서브에이전트 하나, 동시에 최대 3개.** 서브에이전트 지시문에 위 **2번(단계 이동)·5번(브랜치)·12번(막히면 멈춤)** 을 한 줄씩 다시 적는다 — 「스킬대로」 한마디로 맡기지 않는다. 서브에이전트는 머지하지 않는다.
4. 대상이 없으면 「대기 없음」 한 줄만 보고한다. 사용자 판단이 꼭 필요한 건은 루틴이 멈추지 말고 회차마다 「결정 필요: #번호 — 무엇을 고르면 되는지」 한 줄로 올린다.
5. 루틴 허락은 이 요청에 한한다: 사용자가 루틴을 요청한 것이 `dev-<번호>` 브랜치 생성의 허락이다. 푸시·MR 생성은 루틴에서도 하지 않고 로컬 커밋에서 멈춘 뒤 보고한다.

> 등록할 프롬프트: IVE 처리 루틴: ive-handle 스킬의 «처리 루틴»대로 `ive:todo` 이슈 중 내가 담당자인 건을 찾아 서브에이전트로 처리한다. 대상 없으면 한 줄로만 보고.

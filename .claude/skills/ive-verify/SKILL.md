# IVE 이슈 검증 (검증자)

> 짝 스킬: 처리 `ive-handle` · 검증 `ive-verify` · 확인 `ive-confirm`. 단계 라벨의 뜻과 규칙의 이유는 CLAUDE.md 의 「IVE 단계 라벨」 절이 원본이다 — 이 스킬과 다르게 적혀 있거나 프로젝트 자체 규칙이 있으면 그쪽을 따르고 라벨 이름·단계 순서만 이 스킬을 따른다.

검증 = **코드 재검토 + 요청 대조**, 이 둘뿐이다. 화면을 밟아 보는 것은 확인(`ive-confirm`)의 몫이다.
⛔ 자기가 처리한 건은 이어진 문맥에서 검증하지 않는다 — 새 세션에서 이슈와 코드를 처음 보는 것처럼 읽는다.

## 체크리스트 — 이 순서대로

1. **대상을 정한다.** 번호가 없으면 `glab api "projects/kojoung%2Five/issues?labels=ive%3Averify-wait&state=opened"` 로 검증대기 목록을 보여 주고 묻는다.
2. **첫 동작 = 단계 이동.** 코드를 읽기 전에 `ive:verify-wait` → `ive:verifying`. 이동 뒤 단계 라벨이 하나만 남았는지 다시 읽어 본다.
   ```bash
   glab api --method PUT "projects/kojoung%2Five/issues/<번호>" -f "remove_labels=ive:verify-wait" -f "add_labels=ive:verifying"
   ```
3. **요건 목록을 먼저 쓴다.** 본문 + **모든 코멘트**를 시각 순으로 읽고 요건을 한 줄씩 적는다. 보완 코멘트의 시각이 커밋보다 늦으면 그 요건은 코드에 없을 수 있다.
4. **⛔ 처리자의 「완료」를 믿지 않는다.** 노트만 읽지 말고 MR/PR·커밋이 실제로 있는지부터 본다. 없으면 처리되지 않은 것이다.
5. **diff 를 줄 단위로 읽는다.** 이슈 본문·코멘트의 요건과 **1:1 대조표**를 만든다. 범위 밖 변경(무관한 파일·전면 포맷팅·삭제된 테스트)은 지적 대상이다. 공용 부품을 바꿨으면 쓰는 곳을 grep 해 표에 넣고 하나씩 맞는지 본다.
6. **바뀐 쪽 테스트만 돌린다.** 기준선 → 변경 후 → A/B 증적이 노트·MR 에 있는지 본다. 처리 환경에서 **할 수 있었던** 증적이 없으면 반려, **할 수 없었던**(화면·실제 DB·운영) 것은 반려하지 않고 통과 노트의 「확인 요청」으로 옮긴다.
7. **반려는 «머지하면 깨진다»에만.** 요건 누락·명백한 오류·충돌·테스트 실패만 반려한다. 사소한 결함은 직접 고쳐(추가 커밋) 같은 기준으로 다시 본다. 가상의 결함·표현·더 단단히 할 여지는 통과 노트의 「후속」에 적고 머지한다. ⛔ 같은 사유로 두 번 반려하지 않는다.
8. **통과면 머지.** 이 프로젝트의 목표 브랜치는 `main` 입니다. 충돌은 소스 브랜치에서 풀고 테스트를 다시 돌린 뒤 머지하고 개발 브랜치를 지운다.
   ```bash
   glab mr merge <MR번호> -R kojoung/ive --remove-source-branch --yes
   ```
9. **「확인 요청」을 구체화해 노트에 남긴다.** 처리자가 넘긴 것이 모호하면 코드를 읽어 **어디서 · 순서 · 기대 · 아니면 보이는 것 · 필요한 데이터·계정**으로 직접 풀어 쓴다. DDL 이 따르면 머지 **전에** 선적용한다.
10. **결론 단계로 옮긴다.** 통과 → `ive:verifying` → `ive:confirm-wait`(⛔ `ive:done` 로 올리지 않는다 — 완료는 확인 뒤). 못 미침 → `ive:verifying` → `ive:todo` + **파일·줄·고칠 방향**이 든 재작업 지시.
    ```bash
    glab issue note <번호> -R kojoung/ive --message "$(cat note.md)"
    glab api --method PUT "projects/kojoung%2Five/issues/<번호>" -f "remove_labels=ive:verifying" -f "add_labels=ive:confirm-wait"
    ```
11. **`ive-meta` 에 `stage: verify` 를 넣어 노트 끝에 남긴다.** 이 블록이 있어야 검증이 AI 가 한 일로 집계된다(없으면 라벨이 열려 있던 근무시간이 사람 비용이 된다). 형식은 CLAUDE.md 「검증·확인에 쓴 시간과 토큰 남기기」.
12. **막히면 멈춘다.** 판단 근거를 만들 수 없으면 통과가 아니라 멈춤이다 — `ive:verifying` 에 두고 무엇이 필요한지 노트에 적는다.
13. **보고는 10줄 이내.** 첫 줄에 결과(통과·반려·보류) + 현재 라벨.

**확인에서 반려돼 `ive:verify-wait` 로 돌아온 건:** 확인자가 남긴 단서(요소·측정값·이긴 규칙·의심 파일)마다 원인 코드를 짚어 파일·줄·고칠 방향으로 재작업 지시를 쓰고 `ive:todo` 로 넘긴다. 이미 고쳐진 것이 보이면 근거를 적고 확인 요청으로 다시 넘긴다.
**「🔁 반려 반복 — 사람 판단 필요」 건:** 다시 반려하지 않는다. ① 남은 것이 확인 요청뿐이면 머지 → `ive:confirm-wait` ② 구현이 모자라면 한 번에 끝낼 재작업 지시 ③ 요건을 정해야 하면 사용자에게 묻는다.

## 검증 루틴 — 「IVE 검증 루틴 돌려」 라고 했을 때만

`ive:verify-wait`(검증 대기) 이슈를 5분마다 찾아 위 체크리스트로 검증한다.

1. 간격을 따로 말하지 않으면 `/loop 5m <아래 프롬프트>` 로 등록한다(세션이 열려 있는 동안만, 7일 뒤 만료). `CronList` 로 중복 등록을 막고, 등록 직후 한 번 바로 돌린다.
2. 매 회차: `glab api "projects/kojoung%2Five/issues?labels=ive%3Averify-wait&state=opened"` 로 조회해 있으면 **건마다 서브에이전트 하나(동시 최대 3개)** 에 맡긴다. 검증은 서브에이전트가 새 문맥에서 하므로 «자기가 처리한 것을 자기가 통과시키지 않는다»는 원칙이 지켜진다. 대기가 없으면 「대기 없음」 한 줄만 보고한다.
3. 서브에이전트 지시문에 **2번(단계 이동)·12번(막히면 멈춤)** 을 한 줄씩 다시 적는다. 코드 재검토·대조·머지·단계 이동·노트는 그 건의 서브에이전트가 끝까지 하고, 결과(머지 sha 또는 재작업 요지)를 돌려주면 거기서 끝낸다. 다음 건은 새로 띄운다.
4. 막혀서 사용자 결정을 기다리는 건은 회차마다 「결정 필요: #번호 — 무엇을 고르면 되는지」 한 줄로 다시 올린다(조용히 멈춰 서로 기다리는 일을 막는다). 심각한 문제나 꼭 필요한 판단이 아니면 멈추지 않고 끝까지 진행한다.

> 등록할 프롬프트: IVE 검증 루틴: ive-verify 스킬의 «검증 루틴»대로 `ive:verify-wait` 이슈를 찾아 서브에이전트로 검증한다. 대기 없으면 한 줄로만 보고.

확인(`ive-confirm`)은 반영된 환경을 직접 밟아야 해서 루틴으로 돌리지 않는다.
